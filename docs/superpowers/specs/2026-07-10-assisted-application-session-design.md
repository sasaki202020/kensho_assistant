# Assisted Application Session Design

## Goal

承認済みの懸賞を優先順に1件ずつChromeで開き、安全に入力できる項目を自動入力する。ユーザーが外部サイト上で最後の送信を行い、完了を検知できた場合は次の案件へ自動で進む。

## Current Limitation

既存の `prepare-all` は案件ごとにブラウザコンテキストを作成し、入力後に閉じる。最後の1件以外は入力済みページが残らないため、連続応募の操作として成立しにくい。

## Scope

- `APPROVED` または `PREPARED` かつ `approved_by_user=true` の案件だけを対象にする。
- 既存の締切、優先度、応募しやすさの並び順を再利用する。
- 単一の永続Chromeコンテキストで1件ずつ処理する。
- 既存の `form_filler` とプロフィール読み込みを再利用し、安全対象の既知項目だけを入力する。
- 送信前に未解決項目、AI候補、スキップ理由を表示する。
- ユーザーの手動送信と応募完了画面を観測し、確度が高い場合だけ次へ進む。
- 完了判定に確信がない場合は停止し、Web UIの「次へ」で再開できるようにする。
- 手動応募の履歴を既存の `mark_manual_submitted` 経路で記録する。

## Non-Goals

- 外部サイトの送信、確認、応募完了ボタンをコードからクリックしない。
- CAPTCHAを解決または回避しない。
- 同意、年齢確認、メルマガ登録、SNS操作を自動確定しない。
- Cloudflare、bot検知、webdriver検知を回避しない。
- 未承認案件を自動承認しない。
- `profile.enc` の仕様や既存の暗号化方式を変更しない。

## User Flow

1. ユーザーがWeb UIで「今日の応募を始める」を1回押す。
2. アプリが対象案件を締切と既存優先度で並べ、単一Chromeセッションを開く。
3. 先頭案件の応募フォームを開き、安全対象の項目を自動入力する。
4. ブラウザは送信直前で停止し、ユーザーが内容、未解決項目、応募条件を確認する。
5. ユーザーが外部サイト上で必要な手動操作と最後の送信を行う。
6. アプリが手動操作と完了画面を検知できた場合、手動応募として履歴を記録する。
7. 同じChromeセッションで次の案件を開き、手順3へ戻る。
8. 完了を判定できない場合は現在のページを維持し、Web UIに「送信済み・次へ」「保留」「停止」を表示する。

## Architecture

### AssistedSessionRunner

新しい `app/assisted_session.py` にセッションの状態機械を置く。責務は対象案件の選択、単一Chromeコンテキストの維持、入力処理の呼び出し、手動送信の観測、完了判定、次案件への遷移に限定する。

状態は次の値を持つ。

- `IDLE`: 未実行
- `OPENING`: 応募ページを開いている
- `FILLING`: 安全項目を入力している
- `AWAITING_USER_SUBMIT`: ユーザーの確認と送信を待っている
- `VERIFYING_COMPLETION`: 手動操作後の完了画面を確認している
- `AWAITING_USER_NEXT`: 自動判定できずユーザー操作を待っている
- `ADVANCING`: 次案件へ移動している
- `COMPLETED`: 対象案件を処理し終えた
- `STOPPED`: ユーザー停止または重大エラー

### Browser Observation

Playwrightはページを開き、入力し、状態を読むためだけに使う。送信候補要素への `click()`、`press()`、DOM経由の送信、JavaScriptによる `form.submit()` は実行しない。

ブラウザコンテキストに観測用スクリプトを追加し、`event.isTrusted=true` のフォーム送信イベントまたは送信候補へのユーザークリックを通知する。通知後に次の条件を確認する。

- URL、タイトル、本文に応募完了を示す明確な変化がある。
- 手動送信観測より後に完了表示が現れている。
- CAPTCHAエラー、入力エラー、確認画面滞在中ではない。

自動遷移には「信頼された手動操作」と「完了表示」の両方を必須とする。片方しか確認できない場合は `AWAITING_USER_NEXT` にする。

### Field Filling

既存の `fill_campaign_page(..., auto_confirm_known_fields=True)` を再利用する。氏名、フリガナ、郵便番号、住所、電話、メールなど既存の許可項目を入力する。AI候補は既存の候補データがあり、入力許可条件を満たす場合だけ下書きとして入力し、必ずレビュー対象に残す。

次の項目は未解決項目として残す。

- CAPTCHA
- 同意チェック
- 年齢確認
- クイズの確定回答
- メルマガ登録
- 未分類必須項目
- SNS、LINE、ログイン操作

### Local Session Control

セッション状態と制御要求はローカルファイルに保存し、Webプロセスとセッションランナーの間だけで共有する。保存内容にプロフィール値、フォーム入力値、メール、住所、電話番号を含めない。

Web UIから許可する操作は次の3つだけとする。

- `submitted_next`: ユーザーが手動送信済みと明示した現在案件を履歴に記録し、次へ進む
- `hold`: 現在案件を保留して次へ進む
- `stop`: Chromeを維持したまま自動進行を停止する

`submitted_next` は自動応募として記録しない。ユーザーがWeb UIで「送信済み・次へ」を明示的に押した手動応募として扱う。`hold` と `stop` は応募履歴を作成しない。

### CLI and Web UI

CLIに次を追加する。

```text
py -3 main.py prepare-session --status APPROVED,PREPARED --limit 12 --browser chrome
```

Web UIには通常画面の主要操作として「今日の応募を始める」を追加する。実行中は現在案件、進捗、未解決項目、次の行動だけを表示する。内部ステータス名、個人情報、JSONは通常画面に表示しない。

### History and Safety Invariants

- 人間が送信したことを高確度で確認した場合だけ `mark_manual_submitted` を呼ぶ。
- 自動判定できない案件を送信済みにしない。
- `submit_attempted=false`、`submit_clicked=false`、`auto_submitted=false` を維持する。
- `submitted_count_auto=0` を状態、履歴、UIで維持する。
- 例外メッセージと状態メッセージは既存の `privacy_guard` を通す。
- 既存の `prepare`、`prepare-all`、`dry-run`、`later-queue` の入口を変更せず残す。

## Error Handling

- ページ到達不能、フォームなし、重大解析エラーは現在案件だけ停止またはスキップし、理由を残す。
- CAPTCHA、ログイン、SNS条件は自動処理せず、ブラウザを開いたまま人間操作を待つ。
- Chrome終了、セッション切断、Webプロセス再起動時は状態を `STOPPED` とし、再実行で未完了案件から開始できるようにする。
- 完了検知のタイムアウトは応募失敗扱いにせず、`AWAITING_USER_NEXT` にする。

## Testing

- 単一コンテキストで案件が1件ずつ処理されること。
- 入力後に `AWAITING_USER_SUBMIT` で停止すること。
- コードから送信候補をクリックしないこと。
- 信頼された手動操作と完了表示の両方がある場合だけ次へ進むこと。
- 完了表示だけでは手動応募済みにしないこと。
- 完了検知不能時に `AWAITING_USER_NEXT` になること。
- Web UIの `submitted_next`、`hold`、`stop` が意図した状態遷移だけを起こすこと。
- ログと状態ファイルにプロフィール値が含まれないこと。
- `submitted_count_auto` が常に0であること。
- 既存のWeb、フォーム入力、submit controllerテストが通ること。

## Success Criteria

- Web UIの1操作で承認済み案件の連続入力補助を開始できる。
- ユーザーは各案件で外部サイトの確認と最後の送信だけを行える。
- 手動送信完了を確認できた案件は次へ自動遷移する。
- 判定不能時はページを閉じず、安全に人間へ戻す。
- 外部サイトへの自動送信機能は追加されない。
